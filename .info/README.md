# Workspace Intelligence Guide (Control Engineering + AI Development)

## 1) Purpose of this document
This guide is a high-context reference for future development and research in this workspace.
It is written to help both humans and AI agents perform safe, accurate, and efficient changes.

Primary goals:
- Explain the end-to-end control and estimation pipeline.
- Document package responsibilities and interfaces (topics, parameters, launch files).
- Provide reproducible build/run workflows.
- Highlight practical risks and known inconsistencies that can affect experiments.
- Define safe edit boundaries for AI-assisted coding.

---

## 2) Workspace identity and scope
This repository is a ROS2 colcon workspace centered on scaled autonomous racing workflows:
- Simulation and vehicle dynamics execution.
- Controller execution (pure pursuit and teleoperation).
- On-track system identification (Pacejka model identification + LUT generation).
- Tire force benchmarking against IPG CarMaker ground truth.

Top-level folders with active engineering relevance:
- `f1tenth_simulator/`: C++ simulator and support nodes (mux, behavior controller, random walk, keyboard).
- `pure_pursuit/`: Python pure-pursuit controller node and launch.
- `joy_to_ackermann/`: C++ joystick-to-Ackermann converter.
- `On-Track-SysID/`: Python system ID pipeline for Pacejka adaptation and state benchmarking.
- `tire_force_benchmark/`: Python benchmark node for lateral tire force estimation quality.
- `docker/`: container workflow assets.
- `build/`, `install/`, `log/`: generated by colcon; treat as artifacts.

Research/data assets at root:
- `driving_style1.csv`, `driving_style2.csv`, `IPG_waypoint.csv`.
- `environment.yml` for Python scientific stack.

## 3) High-level control/estimation architecture

### 3.1 Runtime dataflow (conceptual)
1. `f1tenth_simulator` publishes vehicle state and sensor topics (including `/odom`).
2. Command producers generate Ackermann commands:
   - `pure_pursuit` -> `/drive`
   - `joy_to_ackermann` -> topic name depends on node config (current code publishes `ackerman` by default).
   - simulator internal channels (keyboard/random/nav) -> selected by mux.
3. `On-Track-SysID` subscribes to `/odom` and Ackermann command topic (default `/drive`) to:
   - collect system-ID training data,
   - run iterative NN-assisted model correction,
   - reload identified Pacejka parameters,
   - publish one-step prediction quality metrics.
4. `tire_force_benchmark` subscribes to `/tire_forces` (CarMaker GT) and compares either:
   - internal Pacejka estimate, or
   - external estimator topic (`Float64MultiArray [FL, FR, RL, RR]`).

### 3.2 Control-theoretic role of each package
- Simulator: plant + sensing + low-level switching/mux behavior.
- Pure Pursuit: geometric path-tracking controller (front-wheel steering command).
- Joy bridge: manual command source for operator-in-the-loop testing.
- On-Track-SysID: model adaptation layer for lateral dynamics and derived LUTs.
- Tire benchmark: estimator validation layer with online statistical metrics.

## 4) Package-by-package deep map

## 4.1 f1tenth_simulator
Type:
- ROS2 `ament_cmake` C++ package.

Build/entry evidence:
- `CMakeLists.txt` builds shared library from `src/*.cpp` and executables:
  - `simulator`
  - `mux`
  - `behavior_controller`
  - `random_walk`
  - `keyboard`
- Launch: `launch/simulator.launch.py`
- Params: `params.yaml`

Key runtime notes:
- Launch starts `joy_node`, `map_server`, lifecycle manager, racecar model, simulator stack, and RViz.
- Keyboard node uses `xterm -e`, requiring terminal/X support.

Important control/dynamics parameters in `params.yaml`:
- Vehicle geometry: `wheelbase`, `width`, `l_cg2front`, `l_cg2rear`.
- Limits: `max_speed`, `max_steering_angle`, `max_accel`, `max_decel`, `max_steering_vel`.
- Tire/handling model constants: `friction_coeff`, `C_S_front`, `C_S_rear`, `mass`, `moment_inertia`.
- Sensor simulation: lidar beams/FOV/noise, update rates.
- Topic map and mux channel configuration.

Research implication:
- This package defines the plant and many effective operating limits.
- Keep parameter consistency with system-ID and controller assumptions to avoid invalid conclusions.

## 4.2 pure_pursuit
Type:
- ROS2 package using `ament_cmake` and installed Python executable script.

Main files:
- `src/pure_pursuit_node.py`
- `launch/pure_pursuit.launch.py`

Core behavior:
- Subscribes to odometry (default `/odom`).
- Reads waypoint CSV (default `driving_style2.csv`).
- Computes nearest waypoint and lookahead target.
- Publishes `AckermannDriveStamped` to configurable drive topic (default `/drive`).

Control details:
- Steering law: classical pure pursuit geometric steering.
- Steering saturation: hard clip at +/- 20 deg.
- Speed output currently set directly to desired velocity in published command.
- A PID-like velocity block is computed but not actually applied to output speed.

Practical caveats:
- Logging each cycle at 50 Hz can create noisy terminal output.
- Waypoint file install/config consistency should be checked for reproducible deployment.

## 4.3 joy_to_ackermann
Type:
- ROS2 `ament_cmake` C++ package with component + node executable.

Main files:
- `src/joy_to_ackermann.cpp`
- `launch/joy_to_ackermann_launch.py`
- `config/params.yaml`

Core behavior:
- Subscribes to joystick messages (`joy`).
- Publishes `ackermann_msgs/AckermannDriveStamped`.
- Supports enable and turbo buttons, dynamic parameter update checks, and safe stop message when disabled.

Important caveat:
- Publisher topic in C++ code defaults to `ackerman` (single n), while much of the workspace control path uses `/drive`.
- Integration requires explicit remap or topic harmonization.

Parameter note:
- `scale_speed` and `scale_speed_turbo` values in config should be validated against expected normal/turbo semantics.

## 4.4 On-Track-SysID
Type:
- ROS2 package with Python node installed via CMake script install.

Main files:
- `src/on_track_sys_id.py`
- `launch/sys_id.launch.py`
- `params/nn_params.yaml`
- `params/pacejka_params.yaml`
- helper modules under `src/helpers/`

Pipeline phases in node:
1. Data collection from odometry + steering command.
2. NN training / model correction (`helpers/train_model.py`).
3. Export CSV dataset.
4. Reload model parameters.
5. Online one-step prediction benchmarking for `v_y` and `omega`.

Published benchmarking topics:
- `/benchmarking/vy_metrics`
- `/benchmarking/omega_metrics`
- `/benchmarking/summary`

Control/dynamics assumptions visible in code:
- Bicycle-model style slip/force computation.
- Pacejka front/rear force models used in prediction step.
- Prediction quality depends on timestamp consistency and low-speed filtering.

Important caveat:
- `setup.py` contains a package name typo (`on_track_sys_"id`) and is not the primary install path here.
- Since installation is CMake script-based, runtime may still work; however packaging metadata is inconsistent and should be fixed before relying on setuptools workflows.

## 4.5 tire_force_benchmark
Type:
- ROS2 `ament_python` package.

Main files:
- `tire_force_benchmark/tire_force_benchmark_node.py`
- `tire_force_benchmark/online_metrics.py`
- `launch/tire_force_benchmark.launch.py`

Modes:
- `internal_pacejka`: computes estimated lateral tire forces from slip angle and normal load.
- `external_topic`: compares external estimator output against CarMaker ground truth.

External mode alignment design:
- Queue-based alignment with configurable sample lead:
  - compare estimate[k] with ground_truth[k + lead]
- Parameters:
  - `external_prediction_lead_samples`
  - `external_max_queue_size`

Metrics per wheel + axle sums + total:
- RMSE, MAE, NRMSE, MaxAE, Bias, StdDev, R2

This package is currently the strongest quantitative validation utility in this workspace.

## 5) Topic and interface contracts

## 5.1 Commonly used topics
- `/odom`: odometry source for controllers and sys-id.
- `/drive`: canonical Ackermann command path in most launch defaults.
- `/tire_forces`: CarMaker tire force ground truth (`hellocm_msgs/TireForcesArray`).
- `/estimated_tire_force_fy`: expected external tire estimator input to benchmark node (`Float64MultiArray`).

## 5.2 Message ordering assumptions
For `tire_force_benchmark` external mode:
- data order must be `[FL, FR, RL, RR]`.
- units expected in Newtons for lateral force.

## 5.3 Synchronization assumptions
- SysID prediction logic uses message timestamps and skips degenerate dt conditions.
- Tire benchmark external mode performs index-shift alignment; choose lead based on estimator horizon.

## 7) Control-engineering interpretation and experiment guidance

## 7.1 Closed-loop testing strategy
Recommended progression:
1. Validate simulator-only dynamics and topic health.
2. Validate command path consistency (`/drive` vs other command topics).
3. Tune pure pursuit lookahead and speed under stable map/waypoint setup.
4. Collect SysID data under sufficiently rich excitation (wide slip-angle coverage).
5. Evaluate model update with benchmark metrics before and after changes.
6. Evaluate tire-force estimator with `tire_force_benchmark` in both internal and external modes.

## 7.2 Key observability and identifiability concerns
- Low-velocity filtering in SysID can reduce low-speed data diversity.
- Excitation richness (steering and speed variation) directly affects parameter identifiability.
- Timestamp quality and topic delay affect one-step prediction error interpretation.
- If command and state topics are out of sync, model fit may be biased.

## 7.3 Benchmark interpretation cautions
- NRMSE is normalized by absolute mean of real signal; near-zero means can produce unstable/NaN normalization.
- R2 can be NaN when real-signal variance is too small.
- Compare metrics at equal operating regimes (speed range, track section, friction condition).

## 9) AI editing protocol for this workspace
Use this as operational guidance for AI-assisted development.

## 9.1 Safe edit zones
Preferred editable sources:
- package `src/`, `launch/`, `config/`, `params/`, `package.xml`, `CMakeLists.txt`, Python package files.

Avoid editing generated artifacts:
- `build/`, `install/`, `log/`.

## 9.2 Pre-edit checklist
Before changing behavior:
1. Identify package owner of the behavior (simulator/controller/sysid/benchmark).
2. Verify topic contract and message types.
3. Verify launch argument defaults and parameter names.
4. Check if metrics consumers depend on current output format.
5. Keep units explicit (radians, m/s, Newtons).

## 9.3 Post-edit validation checklist
After each non-trivial change:
1. Build affected package with colcon.
2. Launch minimal pipeline that exercises modified nodes.
3. Confirm no topic name/type regressions.
4. Check logs for warnings about dropped samples/invalid parameters.
5. Confirm benchmark metrics still publish expected dimensionality.

## 9.4 Change patterns that are usually safe
- Adding launch arguments with conservative defaults.
- Adding optional publishers/subscribers without altering existing topic names.
- Extending metrics outputs with backward compatibility.
- Adding CSV logging fields (appending columns) while preserving existing ones.

## 9.5 Change patterns that require extra caution
- Renaming topics or parameters used across packages.
- Altering wheel order conventions.
- Changing frame conventions or sign conventions for slip/force.
- Editing queue alignment semantics in tire-force benchmark.
- Modifying dynamics equations without synchronized updates in docs and validation scripts.

## 13) Paper Integration: 2411.17508v1 (Learning-Based On-Track SysID)

This section integrates the paper `2411.17508v1.pdf` into this workspace intelligence guide.
It is written to support future code changes that keep the implementation aligned with the method and claims in the paper.

### 13.1 Paper objective and core claim
The paper proposes an iterative on-track system identification method that combines:
- a nominal dynamic single-track model with Pacejka tire forces,
- a residual neural network predicting one-step state error,
- virtual steady-state data generation from the corrected model,
- and least-squares Pacejka fitting on the generated steady-state data.

Main claim:
- robust identification in dynamic on-track conditions,
- low data and compute requirements (about 30 s data and a few seconds adaptation/training),
- better robustness than direct NLS in noisy conditions.

### 13.2 Control model used in the paper
The state/input split in the paper is:
- states: `x = [v_y, omega]`
- inputs: `u = [v_x, delta]`

Dynamic single-track lateral model:
- lateral and yaw dynamics from front/rear lateral forces,
- slip angles from kinematics,
- Pacejka parameters identified are front and rear `[B, C, D, E]` sets.

Discrete one-step prediction is performed by Euler integration.
Residual is defined as measured next state minus nominal model next state.

### 13.3 Iterative learning loop (paper algorithm)
1. Collect on-track data tuple `[v_x, v_y, omega, delta]`.
2. Filter and augment data (including left/right symmetry mirroring).
3. Train NN to predict residual one-step error of nominal model.
4. Build corrected model: nominal + NN residual correction.
5. Generate virtual steady-state data by simulation of corrected model.
6. Recover Pacejka parameters from generated force-slip relation via least squares.
7. Use identified Pacejka as new nominal model and repeat until convergence.

Critical algorithmic idea:
- NN is not the final model artifact.
- NN is used as an intermediate residual model to improve identification of physically interpretable Pacejka parameters.

### 13.4 What is already present in this repository
Strong alignment found in [On-Track-SysID/src/on_track_sys_id.py](On-Track-SysID/src/on_track_sys_id.py):
- data collection on track from odometry + Ackermann command,
- iterative training call chain through helper modules,
- model parameter reload and one-step prediction benchmarking,
- lightweight runtime suitable for fast adaptation.

Related helper structure under [On-Track-SysID/src/helpers](On-Track-SysID/src/helpers) mirrors paper blocks:
- NN definition/training,
- prediction generation,
- Pacejka solving,
- model save/load,
- plotting and metrics.

### 13.5 Gaps and consistency checks for future edits
To keep code-paper consistency high, verify these points before and after edits:
1. Data processing consistency:
- Ensure filtering and symmetry augmentation logic used in experiments is implemented and configurable.

2. Virtual steady-state generation:
- Confirm steering sweep and constant-speed simulation settings match intended operational envelope.

3. Identification objective:
- Keep Pacejka fitting transparent and reproducible (log residuals and fitted coefficients each iteration).

4. Iteration stopping criterion:
- Current convergence in paper is empirical; code should expose measurable stopping options (delta in coefficients, metric plateau).

5. Evaluation metric interpretation:
- One-step RMSE alone may not rank controller-level performance consistently.
- Keep racing metrics (lap time, average/max lateral error) in validation loops.

### 13.7 Recommended modification plan (paper-aware)
If the paper is being extended or modified in this codebase, prioritize:
1. Add explicit experiment manifests:
- save per run: git hash, map, controller parameters, model parameters, data duration, iteration count.

2. Add deterministic iteration reports:
- per iteration export: identified `C_Pf/C_Pr` (or full Pacejka set), RMSE metrics, and race metrics.

3. Add adaptive stopping logic:
- stop if coefficient delta and metric delta remain below thresholds for N consecutive iterations.

4. Improve noise-robust benchmarking:
- add reproducible noise injection utility for simulation benchmarking, matching paper methodology.

5. Harden topic synchronization:
- verify timestamp alignment for state and command data before NN target generation.

### 13.8 Research interpretation notes (control-engineering)
Key strengths of the method:
- preserves physical interpretability through Pacejka parameter output,
- avoids pure black-box dynamics dependence,
- supports rapid re-identification in changing conditions.

Key risks to monitor:
- out-of-distribution behavior outside trained operating regime,
- dependence on data richness (insufficient slip-angle spread limits fit quality),
- mismatch between one-step prediction quality and closed-loop racing performance.

Operational conclusion for this repository:
- treat the iterative corrected-model pipeline as the central research asset,
- preserve strict contracts on signals (`v_x, v_y, omega, delta`) and units,
- validate every algorithmic change with both prediction and closed-loop performance metrics.
